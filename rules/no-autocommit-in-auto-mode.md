Never create a git commit unless the user explicitly asked for a commit in the current exchange. This holds even when Auto Mode (or any "keep going, don't stop to ask" instruction) is active.

Auto Mode's bias toward proceeding without clarifying questions applies to implementation choices — file layout, naming, which library, how to phrase a script's CLI flags. It does not extend to git commits. A commit is a durable, shared-history action: once made it shows up in `git log` for everyone who pulls the branch, and undoing it cleanly (rather than just leaving it) requires a rewrite. Treat "should I commit this" as its own decision point, separate from "should I keep building," and always surface it rather than folding a commit into the same autonomous flow as the rest of the task.

**How to apply:** After finishing implementation work, stop and hand control back with a summary of what changed and what's ready to commit — don't run `git commit` as the last step of a task just because the task is otherwise done and Auto Mode says to keep moving. If the user's original request already contains an explicit commit instruction ("implement X and commit it"), that counts as asking — commit once, don't ask again mid-task. Silent auto-committing (discovered after the fact, e.g. via `git log`) is the failure mode this guards against.
